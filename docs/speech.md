# Спецификация разговорной системы NPC

## Цель

Разговорная система добавляет короткие контекстные реплики для мирных NPC. Это не полноценное дерево диалогов, а фоновая система псевдо-разговоров: NPC замечают игрока, переговариваются между собой, реагируют на опасность, время суток, торговлю, помощь или вред со стороны игрока.

Система должна быть:

- управляемой через данные;
- простой для расширения новыми репликами;
- достаточно тихой, чтобы не засорять экран;
- предсказуемой для отладки;
- не блокирующей игровой процесс.

## Принципы

- Реплики короткие: обычно одно предложение.
- Реплики зависят от контекста: день или ночь, отношение к игроку, враги рядом, торговля, квесты, память NPC.
- Разговоры возникают из событий мира, а не из сложных индивидуальных скриптов.
- Квестово важные сообщения не должны теряться: критичные подсказки остаются в `state.ui.noticeText`.
- Повторы уменьшаются через cooldown и память недавно сказанных реплик.
- У NPC не должно быть длинных монологов в фоновой системе.

## Основные сущности

### Событие речи

Событие речи - причина, по которой NPC может что-то сказать.

Базовые события:

- `greet_player`: NPC заметил игрока рядом.
- `player_known`: NPC уже видел игрока раньше.
- `npc_to_npc_start`: NPC начинает короткий разговор с другим NPC.
- `npc_to_npc_reply`: NPC отвечает другому NPC.
- `danger`: рядом есть враждебные сущности.
- `dwarf_hostile`: гномы переходят в агрессивное состояние к игроку.
- `night`: NPC реагирует на ночь или подготовку ко сну.
- `morning`: NPC реагирует на наступление дня.
- `trade_after`: игрок только что торговал с NPC или фракцией.
- `player_helped`: игрок помог NPC или фракции.
- `player_harmed`: игрок навредил NPC или фракции.
- `quest_hint`: NPC дает короткую контекстную квестовую подсказку.

### Реплика

Реплики хранятся как данные. Реплика описывает текст, условия выбора и вес.

Пример:

```js
{
  id: 'human_farmer_greet_day_first_1',
  group: 'human',
  event: 'greet_player',
  profession: 'farmer',
  tags: ['day', 'friendly', 'first_seen'],
  text: 'Добрый день. Урожай сегодня вроде держится.',
  weight: 1,
  cooldown: 120
}
```

Рекомендуемые поля:

- `id`: уникальный стабильный идентификатор реплики.
- `group`: группа NPC, например `human`, `dwarf`, `waterfolk`, `windfolk`, `underground`.
- `event`: событие речи.
- `profession`: необязательная профессия жителя.
- `kind`: необязательный подтип, например `chief`, `king`, `keeper`, `guard`, `miner`.
- `tags`: контекстные метки для ранжирования.
- `requires`: жесткие условия, которые должны выполниться.
- `excludes`: жесткие условия, при которых реплика запрещена.
- `text`: текст реплики или простой шаблон.
- `weight`: базовый вес при случайном выборе.
- `cooldown`: минимальное время в секундах до повторного использования этой реплики.

### Контекст речи

Перед выбором реплики система собирает контекст.

Пример:

```js
{
  group: 'human',
  profession: 'farmer',
  event: 'greet_player',
  time: 'day',
  phase: 'day',
  playerRelation: 'friendly',
  playerKnown: true,
  enemiesNearby: false,
  tradedBefore: true,
  helpedFaction: false,
  harmedFaction: false,
  alert: false,
  biome: 'plains',
  activeDimension: 'overworld'
}
```

Контекст строится из:

- текущего состояния мира;
- данных NPC;
- памяти NPC;
- памяти фракции или поселения;
- ближайших сущностей;
- активного измерения;
- прогресса квестов.

Функция построения контекста не должна изменять состояние игры.

## Память

### Память NPC

У каждого NPC может быть легкая память речи:

```js
npc.speechMemory = {
  seenPlayer: false,
  lastSpeechAt: 0,
  lastPlayerSpeechAt: 0,
  recentLineIds: [],
  tradedWithPlayer: false
}
```

Эта память нужна для локального разнообразия:

- NPC может впервые поприветствовать игрока;
- NPC может узнать игрока при повторной встрече;
- NPC не повторяет одну и ту же реплику слишком часто;
- NPC помнит, торговал ли именно он с игроком.

NPC, созданные через spawn egg, получают такую же локальную `speechMemory`, как обычные NPC, но без привязки к поселению, если она не задана явно. Для них:

- `seenPlayer` начинается с `false`;
- `tradedWithPlayer` начинается с `false`;
- отношение берется из общей памяти группы, если нет локального поселения;
- квестовые реплики отключены, если NPC не является частью сгенерированной квестовой структуры;
- фразы должны быть более общими, без ссылок на конкретную деревню, дом, короля или квест.

### Память фракции

Долгосрочные последствия лучше хранить на уровне фракции, поселения или конкретной деревни.

Для людей репутация должна быть отдельной для каждой деревни. Игрок может быть другом одной деревни и нежеланным гостем в другой.

Пример:

```js
state.factionMemory = {
  humanVillages: {
    'human-village-0': {
      reputation: 20,
      helped: true,
      harmed: false,
      tradedCount: 4
    },
    'human-village-1': {
      reputation: -15,
      helped: false,
      harmed: true,
      tradedCount: 0
    }
  },
  humansGlobal: {
    reputation: 0,
    helped: false,
    harmed: false,
    tradedCount: 0
  },
  dwarves: {
    reputation: -20,
    helped: false,
    harmed: true,
    tradedCount: 1
  }
}
```

Рекомендуемые уровни отношения:

- `hostile`: `<= -50`
- `wary`: `-49..-10`
- `neutral`: `-9..19`
- `friendly`: `20..59`
- `grateful`: `>= 60`

Где возможно, нужно использовать уже существующие флаги. Например, у гномов уже есть тревога поселения и `hostileToPlayer`; эти значения должны попадать в контекст речи.

Если NPC не привязан к деревне или поселению, система использует общий fallback для его группы, например `humansGlobal` или `dwarvesGlobal`.

## Группы NPC

Первая версия системы рассчитана на мирные и условно мирные группы:

- люди: жители и стражи;
- гномы: шахтеры и стражи;
- водяные: обычные водяные и главный водяной;
- воздушные жители: обычные жители и воздушный король;
- подземные NPC: подземный король и хранители;
- добрый огненный король: событийные реплики после освобождения.

Враждебные мобы и боссы не входят в базовый объем работ. Позже им можно добавить короткие боевые реплики.

## Выбор реплики

Алгоритм выбора:

1. Обнаружить или получить событие речи.
2. Собрать контекст для говорящего NPC.
3. Отфильтровать реплики по `group`, `event`, `profession` и `kind`.
4. Убрать реплики, у которых не выполнены `requires`.
5. Убрать реплики, у которых совпали `excludes`.
6. Посчитать вес каждой оставшейся реплики.
7. Снизить вес недавно сказанных реплик.
8. Убрать реплики, которые еще на cooldown.
9. Выбрать одну реплику weighted random.
10. Обновить память NPC и создать речевой пузырь.

Пример подсчета веса:

```js
score = line.weight || 1
score += matchingTagCount * 2
if (line.tags includes playerRelation) score += 3
if (line.id in npc.recentLineIds) score *= 0.15
if (line.id in globalRecentLineIds) score *= 0.35
```

Жесткая логика должна быть в `requires` и `excludes`. Теги нужны для выбора более подходящей реплики, но не должны отвечать за критичные условия.

## Приоритеты речи

Не все реплики равны. Система должна выбирать реплики по приоритетам, чтобы важные события не терялись под фоновой болтовней.

Рекомендуемые уровни:

1. `critical_quest`: выдача квеста, завершение квеста, выдача важного предмета, изменение основной цели.
2. `danger`: враг рядом, тревога поселения, нападение.
3. `direct_interaction`: торговля, приветствие игрока, реакция на помощь или вред, переход гномов в агрессию.
4. `quest_hint`: необязательная подсказка по уже активному квесту.
5. `ambient`: разговоры NPC между собой, комментарии к времени суток, погоде и месту.

Правила:

- `critical_quest` всегда имеет приоритет над всеми остальными типами речи.
- Если происходит выдача или завершение квеста, фоновая болтовня полностью подавляется на короткий период.
- Пока на экране есть критичное квестовое сообщение, новые ambient-реплики не создаются.
- `danger` подавляет `ambient`, но не подавляет `critical_quest`.
- Если очередь переполнена, низкоприоритетные реплики отбрасываются первыми.

Предлагаемое состояние:

```js
state.speechSystem = {
  globalCooldown: 0,
  ambientMuteTimer: 0,
  lastPhase: null,
  recentLineIds: [],
  eventQueue: [],
  pendingReplies: []
}
```

`ambientMuteTimer` используется для временного отключения фоновой болтовни после квестовых событий, появления босса, тревоги или другого важного события.

Флаг включения фоновой болтовни хранится отдельно в настройках: `state.settings.ambientNpcSpeech`.

## Очередь событий

События речи лучше добавлять в очередь, а не сразу превращать в пузырь. Это позволит сортировать их по приоритету и не терять важные сообщения.

Пример события:

```js
{
  id: 'speech-event-...',
  priority: 'danger',
  event: 'danger',
  speakerRef: { group: 'humans', id: 'human-...' },
  targetRef: null,
  threadId: null,
  createdAt: 123.4,
  expiresIn: 2.0
}
```

Правила очереди:

- события сортируются по приоритету;
- устаревшие события удаляются;
- одинаковые события от одного NPC схлопываются;
- если включен `ambientMuteTimer`, ambient-события не добавляются;
- если выключен `state.settings.ambientNpcSpeech`, ambient-события не добавляются;
- `critical_quest` может вытеснять старые низкоприоритетные пузыри.

## Простые шаблоны

Для разнообразия можно использовать простые шаблоны.

Пример:

```js
{
  text: '{greeting}. У ворот сегодня {gateMood}.',
  vars: {
    greeting: ['Добрый день', 'Здравствуй'],
    gateMood: ['тихо', 'неспокойно', 'ветер пыль гоняет']
  }
}
```

Шаблоны должны оставаться простыми:

- без вложенной грамматики;
- без длинных фраз;
- без важных квестовых фактов в случайных частях;
- с понятным результатом при любой комбинации.

## Речевые пузыри

Реплики показываются как неблокирующие пузыри над NPC или рядом с ним.

Предлагаемое состояние:

```js
state.speechBubbles = [
  {
    id: 'bubble-...',
    speakerRef: { group: 'humans', id: 'human-...' },
    x: 100,
    y: 200,
    text: 'Добрый день.',
    timer: 3.2,
    maxTimer: 3.2
  }
]
```

Правила отрисовки:

- пузырь следует за NPC, если NPC еще существует;
- текст переносится по строкам;
- пузырь ограничивается экраном;
- к концу жизни пузырь плавно исчезает;
- одновременно на экране не должно быть слишком много пузырей.
- речевые пузыри показываются и в мобильном режиме.
- если пузыри накладываются друг на друга, более новый пузырь смещается выше;
- пузыри не должны перекрывать критичные UI-панели сильнее, чем это неизбежно.

Рекомендуемые ограничения:

- максимум активных пузырей: `3`;
- максимум один пузырь на NPC;
- минимальный глобальный интервал между фоновыми репликами: `1.0` секунда;
- минимальный интервал речи одного NPC: `12` секунд;
- минимальный интервал фракционного фона: `5` секунд.

### Настройка фоновых реплик

В меню паузы нужна настройка для отключения фоновых реплик NPC. Название в UI должно быть точным: настройка отключает только ambient-события, но не опасность и не прямые реакции.

Минимальный вариант:

```js
state.settings = {
  ambientNpcSpeech: true
}
```

Поведение:

- если `ambientNpcSpeech === false`, события `ambient`, `npc_to_npc_start`, `npc_to_npc_reply`, `night` и `morning` не создают пузыри;
- `critical_quest`, `danger` и прямые реакции на действия игрока продолжают работать;
- настройка должна сохраняться вместе с остальными настройками игры, если для них уже есть механизм сохранения.

## Разговоры NPC между собой

На первом этапе разговоры между NPC должны быть двухходовыми. Это основной способ создать ощущение, что поселения живут сами по себе.

Условия запуска:

- два мирных NPC находятся рядом;
- NPC принадлежат к совместимой группе или поселению;
- оба не спят;
- оба не дерутся;
- оба не убегают;
- рядом нет срочной опасности;
- оба прошли cooldown речи.

Последовательность:

1. Первый NPC говорит реплику с событием `npc_to_npc_start`.
2. Для второго NPC планируется отложенный ответ через `1.0..2.0` секунды.
3. Второй NPC говорит реплику с событием `npc_to_npc_reply`.

Пример состояния для отложенного ответа:

```js
state.speechSystem.pendingReplies.push({
  speakerRef: { group: 'humans', id: '...' },
  event: 'npc_to_npc_reply',
  replyToLineId: 'human_farmer_chat_work_1',
  timer: 1.4
})
```

Для тематической связки начало и ответ используют `threadId`.

Пример:

```js
{
  id: 'dwarf_chat_start_stock_1',
  group: 'dwarf',
  event: 'npc_to_npc_start',
  threadId: 'dwarf_stock',
  text: 'Сундук у склада считал сегодня?'
}
```

Ответы с тем же `threadId` имеют приоритет при выборе `npc_to_npc_reply`. Если подходящего ответа с `threadId` нет, можно использовать общий ответ без `threadId`.

Дополнительные правила:

- при встрече двух NPC разных профессий можно выбирать реплики по профессии говорящего;
- стражи чаще комментируют ворота, ночь и опасность;
- ремесленные жители чаще говорят о работе, запасах и погоде;
- гномы между собой чаще говорят о шахтах, подпорках, сундуках, факелах и безопасности;
- NPC-to-NPC разговор не должен запускаться, если рядом активен квестовый NPC с важным сообщением;
- один и тот же NPC не должен участвовать в нескольких отложенных ответах одновременно.

## Интеграция с существующими системами

### Торговля

После открытия или успешного завершения торговли:

- пометить `npc.speechMemory.tradedWithPlayer = true`;
- увеличить `factionMemory.tradedCount`;
- при успешной торговле слегка повысить репутацию;
- после успешной сделки попробовать событие `trade_after`.

### Помощь и вред

События `player_helped` и `player_harmed` используются для коротких прямых реакций NPC на отношение игрока.

Правила:

- `player_helped` произносится, когда уже есть факт помощи фракции или поселению;
- `player_harmed` произносится, когда игрок навредил NPC, дому, сундуку или поселению;
- эти события имеют приоритет `direct_interaction`;
- события не должны сами заменять полноценную систему репутации;
- пока полноценная репутация не реализована, эти события могут использовать существующие флаги `helped`, `harmed`, `hostileToPlayer`, `tradedCount` и локальные memory-флаги.

Примеры:

- `Мы помним, что ты помог у ворот.`
- `После того сундука тебе тут не очень рады.`
- `Ты помог. Значит, дорога для тебя чуть шире.`

### Опасность

Если рядом есть враги:

- стражи предпочитают реплики `danger`;
- обычные жители предпочитают испуганные или предупредительные реплики;
- гномы могут предупреждать или переходить к тревоге;
- обычная фоновая болтовня временно подавляется.

### Агрессия гномов

Когда гномы или их поселение переходят в агрессивное состояние к игроку, система должна создать событие `dwarf_hostile`.

Триггеры:

- игрок ударил гнома;
- игрок сломал защищенный блок колонии;
- игрок украл из сундука гномов и был замечен;
- поселение выставило `hostileToPlayer = true`.

Правила:

- событие `dwarf_hostile` имеет приоритет `direct_interaction`;
- при первом переходе поселения в агрессию должна прозвучать короткая реплика предупреждения или угрозы;
- реплика должна быть одноразовой на конкретный переход в агрессию, чтобы гномы не кричали каждую секунду;
- после агро-реплики обычная ambient-болтовня гномов подавляется;
- пока гномы враждебны, их последующие фразы должны идти через `danger` или будущие боевые реплики, а не через обычный ambient.

Примеры:

- `Не трогай наши стены. Теперь отвечай.`
- `Вор у сундуков! Закрыть проходы!`
- `К оружию, он пошел против колонии.`

### Сон и время суток

Реплики могут появляться:

- при наступлении ночи;
- когда NPC идет домой или к кровати;
- утром после ночи;
- когда NPC просыпается.

У таких реплик должны быть длинные cooldown, чтобы ночь не сопровождалась постоянным шумом.

Утренние реплики создаются событием `morning`, когда фаза мира переходит из `night` в дневную фазу. Это ambient-событие и отключается настройкой `ambientNpcSpeech`.

### Квесты

Квестовые NPC продолжают использовать текущие notice-сообщения. Квестово важные события имеют абсолютный приоритет и не должны теряться.

Правила:

- выдача квеста, завершение квеста и выдача важной награды считаются `critical_quest`;
- `critical_quest` может создать речевой пузырь, notice-сообщение или оба канала сразу;
- если начинается `critical_quest`, ambient-болтовня временно выключается через `ambientMuteTimer`;
- при выдаче квеста NPC-to-NPC разговоры не запускаются;
- квестовые сообщения не вытесняются более низким приоритетом;
- если нет места для нового пузыря, ради `critical_quest` можно удалить самый старый ambient-пузырь.

Пример условий для квестовой реплики:

```js
requires: {
  activeDimension: 'water',
  waterQuestGiven: true,
  hasMedicine: false
}
```

### Невидимость

Если игрок незаметен для NPC:

- NPC не приветствуют игрока;
- NPC не реагируют на его близость;
- NPC-to-NPC разговоры могут продолжаться.

## Предлагаемая структура файлов

Новые файлы:

- `src/systems/speech.js`: обновление системы речи, сбор контекста, выбор реплик, память.
- `src/data/speechLines.js`: база реплик.
- `src/render/speechRenderer.js`: отрисовка речевых пузырей.

Изменяемые существующие места:

- `src/core/state.js`: начальное состояние `speechBubbles`, `speechSystem`, `factionMemory`.
- `src/main.js`: вызов обновления системы речи.
- `src/render/renderer.js`: вызов отрисовки речевых пузырей.
- `src/render/pauseRenderer.js`: настройка включения/отключения фоновой болтовни.
- `src/systems/crafting.js` или `src/systems/trade.js`: событие после успешной торговли.
- `src/systems/interaction.js`: события после удара по мирному NPC, если понадобится обновлять репутацию.

Основная логика должна жить в `speech.js`, а не размазываться по всем файлам NPC.

## MVP

Первая версия должна включать:

1. Отрисовку речевых пузырей.
2. Data-driven базу реплик.
3. Общий update-loop разговорной системы.
4. События:
   - `greet_player`
   - `npc_to_npc_start`
   - `npc_to_npc_reply`
   - `danger`
   - `dwarf_hostile`
   - `night`
   - `morning`
   - `trade_after`

   - `player_harmed`
5. Память NPC:
   - `seenPlayer`
   - `lastSpeechAt`

## Дополнительные правила и риски

### Сохранения

Нужно решить, какие данные попадают в сохранение:

- репутация деревень и фракций должна сохраняться;
- настройка `ambientNpcSpeech` должна сохраняться;
- локальная память NPC может сохраняться, если NPC уже сохраняются как часть мира;
- активные пузыри сохранять не нужно;
- pending replies сохранять не нужно.

### Производительность

Система не должна каждый кадр проверять все пары NPC.

Рекомендации:

- запускать тяжелую проверку ambient-событий не чаще нескольких раз в секунду;
- ограничивать число NPC-кандидатов около игрока;
- для NPC-to-NPC разговоров проверять только сущности в пределах экрана или радиуса вокруг игрока;
- не строить сложные списки всех пар NPC без необходимости.

### Читаемость

Пузырь должен быть читаемым на любом фоне.

Требования:

- контрастная подложка;
- ограничение ширины;
- перенос строк;
- защита от выхода за экран;
- короткое время жизни;
- отсутствие перекрытия критичных UI-панелей по возможности.

### Шум

Разговорная система должна быть редкой, а не постоянной.

Правила:

- NPC не должен говорить каждый раз, когда игрок проходит мимо;
- первая встреча может быть более вероятной, повторная встреча реже;
- если игрок стоит в деревне, фразы должны постепенно затихать через cooldown;
- при открытом крафте, торговле, паузе или game over фоновую болтовню лучше не создавать.

### Авторинг реплик

Чтобы реплики не выглядели случайным набором фраз:

- у каждой группы должен быть свой тон;
- профессии жителей должны влиять на лексику;
- гномы должны чаще говорить о шахтах, камне, запасах и безопасности;
- водяные - о воде, болезни, колодцах и замке;
- воздушные жители - о ветре, облаках, паре, ворах и замке;
- реплики не должны обещать механику, которой нет в игре.

## Принятые решения

- Речевые пузыри показываются в мобильном режиме.
- В паузе нужна настройка для отключения фоновой болтовни.
- Квестово важные события имеют абсолютный приоритет.
- Во время выдачи или завершения квеста фоновая болтовня не запускается.
- NPC, созданные через spawn egg, получают локальную память речи, но без квестовой и деревенской привязки.
- Репутация людей хранится отдельно для каждой деревни.
- Когда гномы становятся агрессивными к игроку, они должны произносить короткую агро-реплику.
- Когда мирные NPC встречаются между собой, они могут запускать короткий двухходовой разговор.
- NPC-to-NPC разговоры используют `threadId`, когда есть тематическая пара.
- Утренние реплики входят в базовое поведение.
- Настройка в паузе называется как отключение фоновых реплик, а не всех реплик NPC.
- Помощь и вред представлены событиями `player_helped` и `player_harmed`; полноценные изменения репутации остаются отдельной будущей задачей.
